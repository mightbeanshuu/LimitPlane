# LimitPlane XDP fast path

A second, much cheaper layer in front of the gateway. An XDP program sits in
the network driver and drops two kinds of traffic **before the kernel
allocates an `sk_buff` for it**:

1. **Banned addresses.** When the gateway's autopilot puts a client in
   cooldown (a retry storm: 10 burst-blocks in 60 s), the agent copies that ban
   into a BPF map and the NIC starts dropping the client's packets. The Go
   layer no longer pays a TCP handshake, a goroutine, an HTTP parse and a 429
   for a client it has already decided to ignore.
2. **Per-IP floods.** A plain token bucket per source address (packets/second
   + burst), refilled from `bpf_ktime_get_ns()`.

Everything that needs meaning — tenants, API keys, cost classes, monthly
plans, fingerprinting — stays in Go. **The kernel drops what is obviously bad;
the gateway decides what is subtly bad.**

```
 packet ─▶ NIC driver ─▶ [ XDP: banned? flood? ] ──drop──▶ (gone, ~no cost)
                                │ pass
                                ▼
                         kernel TCP/IP ─▶ LimitPlane gateway (Go) ─▶ your app
                                                  │
                         limitplane-xdp ◀─────────┘ GET /v1/admin/autopilot
                         (writes the ban map every second)
```

This directory is its **own Go module** (it needs `github.com/cilium/ebpf`),
so the gateway itself stays dependency-free and its CI gate is unchanged.

## Files

| | |
|---|---|
| `bpf/fastpath.c` | the XDP program: parse → banned? → bucket → pass |
| `fastpath/` | Go loader: load, pin maps, attach (native → generic fallback), ban/unban, counters. `fastpath_bpfel.{go,o}` are generated by `go generate` (bpf2go) and committed, so building needs Go, not clang |
| `cmd/limitplane-xdp/` | the agent: attach + sync loop + Prometheus metrics, and `ban` / `unban` / `stats` subcommands |
| `test.sh` | end-to-end proof on a real kernel with network namespaces |

## Run

Linux, root (or `CAP_BPF` + `CAP_NET_ADMIN`), bpffs mounted at `/sys/fs/bpf`.

```bash
cd xdp
go build ./cmd/limitplane-xdp

# attach, and mirror the gateway's cooldowns (needs a JWT for /v1/admin/autopilot)
LIMITPLANE_EMAIL=... LIMITPLANE_PASSWORD=... \
  sudo -E ./limitplane-xdp -iface eth0 -gateway http://localhost:3000 \
       -rate 2000 -burst 4000 -never 10.0.0.0/8

# or, in front of a real site: the reverse proxy, read with its adminKey
LIMITPLANE_ADMIN_KEY=... sudo -E ./limitplane-xdp -iface eth0 \
       -gateway http://127.0.0.1:80     # proxy started with: limitplane --config lp.json

sudo ./limitplane-xdp ban 203.0.113.7 -for 10m   # operator ban, by hand
sudo ./limitplane-xdp unban 203.0.113.7
sudo ./limitplane-xdp stats                      # passed / dropped_banned / dropped_rate
curl -s localhost:9091/metrics                   # same counters, Prometheus text
```

Ctrl-C / SIGTERM detaches the program. The maps stay pinned under
`/sys/fs/bpf/limitplane`, so a restarted agent keeps the same bans.

## Test

```bash
sudo bash xdp/test.sh
```

Builds both binaries, creates two network namespaces joined by a veth pair,
and proves on the real kernel: normal v4 + v6 traffic passes; a banned
address is dropped (v4 and v6) while its neighbour is not; a timed ban
expires in the kernel with no agent involved; a 5,000-packet UDP flood is cut
to exactly the burst; other sources are unaffected and the flooder recovers
once its bucket refills; the metrics endpoint exports the counters; SIGTERM
detaches the program; and, end to end, a storm against the real gateway gets
the client a cooldown that the agent copies into the kernel.

Last run: **all 17 checks passed** on Linux 6.8.0 (aarch64, Ubuntu 24.04 in a
Colima VM), with the program attached in **native** mode on the veth.

**On the public internet:** [`azure/`](azure/) runs the reverse proxy in front
of a demo shop on an Azure VM (kernel 7.0, `hv_netvsc`, generic mode) while a
second VM attacks it. The attacker forged `X-Forwarded-For`, got itself (not
the forged address) banned, was dropped at the NIC 4 s after it started, and a
20,000-packet UDP flood was cut to its burst. The full session log is there.

## Design notes

- **Why XDP and not iptables/nftables.** Netfilter runs after the skb exists
  and after the packet has walked part of the stack. XDP runs in the driver on
  the raw frame, so a drop is a few tens of nanoseconds and allocates nothing.
  It is also programmable: the ban list is a map that Go writes, not a rule
  set that has to be rebuilt.
- **LRU maps.** The keys are source addresses — attacker-controlled. A plain
  hash map fills up and then refuses inserts, which a spoofed-source flood
  could do on purpose. An LRU evicts the least recently seen address instead.
- **Bans expire in the kernel.** Each ban carries a `CLOCK_MONOTONIC` deadline
  (the clock `bpf_ktime_get_ns` reads). If the agent crashes, its bans still
  lapse on time, and the program deletes them as it meets them.
- **The bucket is approximate, on purpose.** It is updated through a pointer
  with no lock, so two CPUs handling the same source at once can lose an
  update. A spin lock per packet would serialise exactly the flood this is
  for. RSS sends one flow to one RX queue, so a single connection is always
  one CPU; only a source spraying many flows sees the approximation. The exact
  limit is still the Go layer's job.
- **Only anonymous clients become kernel bans.** `anon:<ip>` tenants are
  identified by their address, so banning the address is exact. A named
  tenant is an API key, possibly behind a NAT shared with other customers, so
  those cooldowns stay in Go where the key is visible.
- **Native first, generic fallback.** Native mode runs in the driver; generic
  mode works on any interface but runs after skb allocation, so it saves
  less. The agent logs which one it got.

## Limits (honest)

- **L3 only.** It knows source addresses and packet counts — nothing about
  TCP state, HTTP, paths or API keys. It is not a WAF.
- **Trust in X-Forwarded-For.** The demo gateway takes an anonymous client's
  address from `X-Forwarded-For`, which a client can forge. The reverse proxy
  ignores that header unless started with `--trust-proxy`, so on an
  internet-facing host a forged header cannot get somebody else banned (the
  Azure run below checks exactly this). Behind your own load balancer, pass
  `--trust-proxy` and put the balancer in `-never`. `-max-bans` caps how many
  gateway bans reach the kernel.
- **Behind a load balancer it does little:** the NIC sees the balancer's
  address, not the client's.
- **The bucket counts packets, not requests or bytes.** Set the rate well above
  what a legitimate client sends; it is a flood guard, not the rate limit.
- **Linux only**, root or `CAP_BPF` + `CAP_NET_ADMIN`. IPv4 and IPv6 over
  Ethernet; VLAN-tagged frames and everything else are passed untouched.
- Tested in namespaces (6.8) and on one Azure VM (7.0, generic mode). Not yet
  run against production traffic.
